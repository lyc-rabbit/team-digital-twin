# 场景与故事线 · 预期清单

本文把产品从「能做什么」收成「谁在什么情况下会得到什么」。开源宣传、演示脚本、验收都可以对照这里。

相关界面按左侧导航分组：**看团队 / 做项目 / 带人成长 / 看关系 / 推演 / 配置**。

---

## 1. 产品在讲什么故事

团队数字孪生不是再做一个组织通讯录，也不是把日报丢进大模型聊天。

它要回答的问题是：

> 现实里发生了什么？系统凭什么这样认为？由此能看出谁真正做了什么、谁在带人、谁只是挂名负责？

主干故事线只有一条：

```
发生了什么（事件 / 日报 / 文档）
        ↓ 记录，不直接改图
待确认事实 Fact（主谓宾 + 来源 + 时间）
        ↓ 人确认
知识图谱（责任 / 成果 / 贡献 / 培养 / 能力证据）
        ↓ 禁止跨语义域瞎推
分析与推演（态势、关系网、晋升、模拟实验室）
```

总规则（必须始终成立）：

| 不得从…推出 | 不得得到… |
|---|---|
| 职位高、汇报关系 | 培养了下属 |
| 成果挂在谁名下 | 谁实际做了技术 |
| 项目 OWNER / 管理责任 | 具备该项目全部能力 |
| 向领导汇报了成果 | 创造了成果 |
| 做过一次贡献 | 已经掌握对应能力 |

## 2. 角色与入口

| 角色 | 他们关心什么 | 主要入口 |
|---|---|---|
| 团队负责人 | 今天稳不稳、谁过载、项目会不会爆 | 团队态势、日历、模拟实验室 |
| 项目经理 | 谁在做、卡在哪、风险是什么 | 项目中心、日报、事实管理 |
| 带教者 / 干部 | 新人卡在哪、授权够不够、向上协同 | 新人地图、干部成长、向上协同 |
| 贡献者本人 | 自己的执行和贡献有没有被记下来 | 记录事件、日报、日历 |
| 治理 / 研究者 | 图谱有没有乱推、实体是否同一人 | 事实管理、本体治理、实体治理、时间轴 |

全局悬浮按钮 **记录事件** 在几乎所有页面都可用。预期：记完先进日历，并生成**待确认事实**；确认后才写图谱关系。

## 3. 主干故事线（演示推荐顺序）

下面是一条可从头演示到尾的故事。人名可换成你自己团队的人。

### 故事背景

产品线要上线「AI 客服一期」。编制上领导 A 是项目负责人，工程师 B 做架构和核心开发，领导每周给业务汇报进度。同时领导是 B 的上级。

**现实：**

- 成果客观存在：AI 客服一期上线。
- 领导：组织挂名 + 管理节奏 + 成果汇报。
- 工程师：执行落地 + 技术/架构贡献。
- 领导**没有**因为「是上级」就自动算培养了 B。

### 步骤与预期

| 步 | 操作 | 预期看到 |
|---|---|---|
| 1 | 成员管理里录入领导 A、工程师 B | 人员出现在所有人员下拉框 |
| 2 | 记录事件：B 完成接口与上线，A 做周报汇报 | 日历出现事件；事实管理出现待确认事实 |
| 3 | 事实管理确认：拆开「组织责任 / 执行责任 / 汇报责任 / 技术贡献」 | 已确认事实写入图谱；**不要**只确认一条笼统「负责」 |
| 4 | 人物关系网查看 | A：管理/汇报/归属；B：执行 + 技术贡献。没有 A→B 的培养边 |
| 5 | 本体治理 → 语义分析 | 若历史图把汇报当成培养、把 OWNER 当成贡献，出现「撤销非法推理」工单 |
| 6 | 团队态势 / 晋升画像 | A 管理与汇报证据强、技术贡献弱；B 执行与技术证据强、培养他人待定 |
| 7 | 模拟实验室：「我要晋升管理岗位」选 B | 准备度看执行/专业证据，不因为没当 OWNER 就判零 |

### 失败形态（演示时用来对比）

如果系统还在用「A 是负责人所以 A 有技术能力」「A 是上级所以 A 培养了 B」，说明非法推理没有被拦住，应去本体治理处理工单，而不是信分析结论。

## 4. 场景清单与预期

每一条都写成：**谁、从哪进、做什么、系统不得做什么、成功长什么样**。

### 4.1 看团队

#### S1 今天团队怎么样了

- **谁：** 负责人，每天上班先打开系统。
- **入口：** 团队态势 → 今日总览。
- **做：** 看人员动向、项目态势、风险；必要时补「今日特殊事项」。
- **不得：** 把未确认推断当成已经发生的事实；自动改职级或绩效。
- **预期：** 能分出正常 / 关注 / 风险；风险带来源（项目、人员、协作等）；点进卡片能追到事件或日报，而不是一句空评语。

#### S2 翻历史：哪天发生过什么

- **入口：** 日历。
- **做：** 日/周/月浏览；点空白日期或「记录事件」写草稿。
- **预期：** 只展示 `team_events`；保存后事件马上出现在对应日期。时区按北京时间。

#### S3 总览关系与情绪

- **入口：** 总览。
- **做：** 看健康度、3×3 关系网格、成员情绪。
- **预期：** 网格来自事件回放与衰减，不是大模型现场编分。点一对人能看到证据明细。

#### S4 日报进孪生

- **入口：** 日报。
- **做：** 导入或查看日报，看到项目投入、技能。
- **预期：** 重建图谱时，投入最多的人得到 **执行责任**，不再被当成项目 OWNER / 技术全能。共同投入会形成协作，不形成培养。

---

### 4.2 做项目

#### S5 项目里记下一次交付或卡点

- **入口：** 项目中心 → 记录事件（来源会带上项目）。
- **做：** 选类型/标签，按框架写背景、事实、动作、结果。
- **预期：** 事件关联该项目；待确认事实可含 `WORKS_ON` / `EXECUTION_RESPONSIBILITY`；**不要**自动给「投入最多的人」写技术贡献。

---

### 4.3 带人成长

#### S6 新人卡住了

- **入口：** 新人地图。
- **做：** 建新人、看必须介入 / 建议介入；用记录事件写下指导或问题。
- **预期：** 介入级别来自阶段与证据，不是职级。事件里写了「指导」应走向 **培养行为 TrainingAction**，而不是给所有在场的人两两连上 MENTOR。

#### S7 干部有没有被验证过

- **入口：** 干部成长。
- **做：** 看「已验证 / 形成中 / 未验证」。
- **预期：** 「已验证」要有能力证据或结构化事件，不能仅因为头衔含「负责」「经理」。

#### S8 和上级处得怎么样

- **入口：** 向上协同：上级关系 / 信任 / 授权 / 汇报 / 风险。
- **做：** 看判断依据和引用事实。
- **预期：** 汇报多 ≠ 被培养；信任变化能点到具体事件。

#### S9 角色卡与晋升推演

- **入口：** 角色卡、晋升领导。
- **做：** 对照 AI Native 角色要求，做晋升模拟。
- **预期：** 领导力/专业分可解释（能力、投入、被信任、影响力、冲突）。OWNER 次数不再直接加「交付/技术」分。界面应说明这是推演参考，不是 HR 正式评价。

---

### 4.4 看关系（治理主干）

#### S10 记一件事 → 待确认事实 → 写图

- **入口：** 任意页 FAB / 日历草稿 → 事实管理。
- **做：** 保存事件后去「待确认」勾选、处理冲突、确认。
- **预期：**
  - 日历有事件。
  - 事实带来源「事件 · …」。
  - 互斥谓词（组织责任、汇报等）时间重叠且主体不同 → 冲突，不能确认。
  - 确认才出现图谱边；删除事实：软删 + 仅该事实支撑的边可删 + 下游 STALE，**默认不自动重跑分析**。

#### S11 从纪要抽取关系

- **入口：** 人物关系网 → LLM 关系抽取。
- **做：** 粘贴纪要，抽 3 次去重，勾选后「确认写入事实」。
- **预期：** 先登记事实再写图，不绕过事实层。模型不得因「上级」输出培养，不得因「负责人」输出技术贡献。冲突则留待处理。

#### S12 文档抽取事实（不直接成网）

- **入口：** 事实管理 → 抽取事实 / 录入事实。
- **做：** 抽主谓宾，人确认。
- **预期：** 抽取结果是 EXTRACTED，不是关系网。同一三元组与关系网抽取共享 `origin_key`，不重复插。

#### S13 同一人、同一项目、同一成果不要裂开

- **入口：** 实体治理。
- **做：** 合并候选、别名、确认同一实体。
- **预期：** 不物理删节点；不改图节点 `type`。人不能从本体里「下线」。

#### S14 本体与非法推理

- **入口：** 本体治理：语义分析、工单、类型、属性、关系、约束。
- **做：** 分析后处理「撤销非法推理」工单。
- **预期：**
  - 新增类型可被声明：成果、贡献、培养行为、能力证据、项目阶段。
  - 「负责」在关系 Schema 里拆成组织/执行/管理/汇报责任。
  - 规则 `ContributeViaProjectDept` 为停用。
  - 确认撤销 → 只删推断边，不删节点、不改 type。
  - LLM 不直接写图；写图必须经确认工单或已确认事实。

#### S15 关系随时间变化

- **入口：** 时间轴分析。
- **做：** 看某日 OWNER / 执行责任是否有效。
- **预期：** 时间是关系/事件的属性，不是一种实体。交接会关掉旧区间、打开新区间。非重叠时间的互斥谓词不算冲突。

### 4.5 推演

模拟实验室以**规则计算**为主，LLM 只写摘要，不打分。

| ID | 场景 | 预期 |
|---|---|---|
| `mentor_people` | 我要带新人 | 给出跨度、依赖、培养压力；**不**把现有汇报关系当成已经在带人。 |
| `own_project` | 我要负责项目 | 区分挂名负责 vs 执行负责；负荷与授权风险可解释。 |
| `promotion` | 我要晋升管理岗位 | 准备度、缺口、观察线时间；技术贡献与管理责任分开列。 |
| `expand` | 团队扩大 | 加人后的管理跨度、导师缺口、瓶颈人。 |
| `departure` | 人员调岗 / 离开 | 项目单点、新人断档、知识单点。 |
| `custom` | 自定义「如果…」 | 尽量归入上面场景；否则给带证据的叙述，不编造图谱里没有的关系。 |

智能对话：用历史事件和关系回答「谁和谁紧张」「合作风险」。预期引用事实，而不是空泛性格分析。

#### S16 成员管理

- **做：** 增改人员、人设、决策风格。
- **预期：** 无预置 Mock 人设。人设影响推演话术，**不能**单独证明能力或贡献。

## 5. 图谱里「同项目两人」应长什么样

对应宣传图「挂名 vs 贡献」。

```
领导 A
├── MANAGEMENT_RESPONSIBILITY → 项目 X
├── REPORTING_RESPONSIBILITY → 项目 X / 成果 X
└── ACHIEVEMENT_OWNERSHIP → 成果 X
    （到此为止。禁止再自动连技术贡献或培养）

工程师 B
├── EXECUTION_RESPONSIBILITY → 项目 X
├── MADE_CONTRIBUTION (technical / architecture) → Contribution
│       └── CONTRIBUTES_TO → 成果 X
└── WORKS_ON → 项目 X
```

分析层应读出：

| 人 | 项目管理证据 | 成果汇报 | 技术贡献 | 培养他人 |
|---|---|---|---|---|
| 领导 A | 强 | 强 | 弱 | 弱（除非另有 TrainingAction） |
| 工程师 B | 弱 | 弱 | 强 | 待定 |

## 6. 跨页一致性（回归时必看）

改了「事实怎么写」之后，下面这些读端必须仍一致：

1. 日历只读事件，不把未确认事实画成日程。
2. 人物关系网默认计算不采用未确认推断边。
3. 晋升 / 态势 / 影响力不把 OWNER、汇报、成果归属当成技术或培养。
4. 删除或替代已确认事实后，下游标失效，分析不偷偷重跑（除非用户点重建）。
5. 重建图谱：回放已确认工单；未确认推断不得写回。

## 7. 演示 10 分钟脚本

1. 打开团队态势，说明「先看今天」。
2. 记一条上线事件（带领导与工程师）。
3. 事实管理确认：拆责任与贡献。
4. 关系网指出两边语义不同。
5. 本体治理扫一眼禁止规则。
6. 模拟实验室跑「晋升」或「带新人」，展示判断依据引用了哪些事实。

结束语可以用总规则原句：

> 事实可以证明事实；事实不能跨语义域无条件推理。
